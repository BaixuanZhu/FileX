# Backlog（v2 移出项与重启条件）

被 v2 瘦版策略移出本轮范围的条目。**不是丢弃，是等证据**。
每项都写明"什么情况下值得重启"，避免下次重新从零辩论。

## B1 审批队列（非交互场景的人工审批通道）

- **原计划**：`~/.filex/approvals/` 落盘待审请求 + `filex approve` / `deny` + TTL 超时转拒绝。
- **移出理由**：覆盖的场景是"人在旁边但不在同一个终端"，对本地单用户 CLI 几乎不存在。引入新状态机 + Agent 静默挂起风险（需要 TTL 兜底），换来的边际安全收益很小。tty 提示 + 非交互拒绝已覆盖真实场景。
- **重启条件**：出现以下任一
  - 有用户在**远程/无终端**环境（CI、容器、守护进程）运行 filex 并明确需要人工放行；
  - 观测数据显示非交互 deny 频繁阻断真实有效的任务（即 deny 不是误操作而是正常需求）。
- **预估**：M

## B2 审计哈希链（`prev_hash` / `entry_hash` + `journal verify`）

- **原计划**：链式哈希 + `filex journal verify` 定位断裂行。
- **移出理由**：**无外部锚点或签名密钥的哈希链，对本地攻击者是安全剧场** —— 能改日志的人也能重算整条链。真实价值是检测意外损坏与半截写入，不是防篡改。按这个价值定位，它是可选小项，不该挂在"防篡改审计"的名义下推进。
- **重启条件**：
  - 日志被用作**对外证据**（如上报到远程服务、作为合规材料）→ 此时需要的是远程锚定或签名，而非本地链；
  - 实际遇到 JSONL 半截写入/损坏问题，需要结构校验工具。
- **注意**：若重启，必须同时决定锚点方案（远程 append-only 存储 / 定期签名摘要），否则仍是剧场。
- **预估**：S（纯本地链）/ M（含锚点）

## B3 分类规则引擎（`guard.classes` 配置化）

- **原计划**：`~/.filex/config.json` 的 `guard.classes` 数组，支持 verb / path glob / batch size 匹配与 interactive/non-interactive 分别决策。
- **移出理由**：v2 的高危类只有 3–5 个且稳定（purge 删除、machine 作用域环境变量写、覆盖 filex 自身配置）。为 5 个硬编码类建通用规则引擎是典型的过早抽象；规则引擎当初一半动机是服务已被移出的预算规则。
- **重启条件**：出现第 6–7 个高危类，或有用户需要自定义高危路径。
- **当前替代**：硬编码默认类 + `guard.enabled` 开关 + bypass 旗标。
- **预估**：M

## B4 执行预算拦截与降级阶梯

- **原计划**：`~/.filex/sessions/` 跨进程计数存储 + 四档降级（allow→confirm→readonly→deny_destructive）+ TTL 自动恢复。
- **移出理由**：计数键（会话身份）不可靠 —— `ppid` 派生对每次新进程的 Agent 失效、对同终端手工用户误伤。键不可靠则配额判定基础不成立。用全计划最复杂的跨进程锁 + 状态机换一个基础不牢的防护，不划算。
- **重启条件**：`10-30-session-usage-observability` 的决策门判定为"值得拦截"，即观测数据同时满足
  - `session_source` 中真实会话标识（非 absent）占比足够高，说明键可靠；
  - 存在 p99 远超安全阈值的消耗分布，说明"单动作合法、合起来异常"是真实现象而非假想。
- **预估**：M→L

## B5 能力令牌（短时效、绑定路径与操作）

- **原计划**：`guard.Capability` 接口预留 + 配置位。
- **移出理由**：v2 连接口都不预留 —— 预留一个不会被实现的接口只会订下难改的协议形状，且会给读者"已支持"的错觉。
- **重启条件**：确实出现多主体授权需求（如多个 Agent 共享一台机器且需要不同能力边界）。
- **预估**：L

## B6 `filex trash list` / `filex trash restore`

- **现状缺口**：`rm` 默认移入 `~/.filex/trash`（`internal/ops/file_ops.go:348`），但**没有任何恢复命令**，用户只能手动翻目录。
- **移出理由**：与三项增强主线无关，但它是"回收站是事后恢复"这一说法的实际支撑 —— 没有 restore，"可恢复"是半成品。
- **重启条件**：建议**尽快作为独立小任务做掉**，优先级高于 B1–B5。
- **预估**：S

## B7 `policy.Config.BackupBeforeWrite` 死配置

- **现状**：`policy.go:13` 定义且默认 `true`，但**无任何调用点**；write 仅在显式 `--backup` 时备份（`file_ops.go:255`）。README 的描述与代码冲突。
- **处置要求**：**要么实现、要么删除，不留半成品**。倾向删除（`--backup` 显式语义更清晰），同步修正 README。
- **重启条件**：无需等待，建议随熔断子任务的文档阶段一并清理。
- **预估**：S
- **2026-10-30 复核**：文档侧冲突已消失 —— README × 2 与 `help.go` 都不再提到 `backup_before_write`，只剩 `policy.go:13`、默认值和两处 `policy_test.go` 引用它。**代码侧仍未处置**：删除它是一个配置兼容性变更（用户 `policy.json` 里若写了这个键，删除后会被判为未知字段），不适合塞进本轮以"加熔断"为主题的改动里。

## B8 `backup prune` 是否纳入熔断分类

- **现状**：熔断阶段 D2 计划把 `backup prune` 接入 `gate`，实际**未接**。`prune` 删的是备份副本，不是用户数据本身，且执行有审计（`backup_prune` 记录保留策略与删除条数）。
- **移出理由**：分类判据是"该动作是否造成不可逆的用户可见后果"。为 `prune` 硬造一个类别会让这条判据变成"凡是删东西的都门控"，进而要求把 `trash` 清理、日志轮转等一并纳入 —— 那正是 B3 规则引擎该解决的问题，不该靠往硬编码表里塞条目来应付。
- **重启条件**：出现第 6 个高危类（B3 的重启条件）时一并评估；或真实发生"Agent 跑 prune 把用户唯一备份清掉"的案例。
- **预估**：S

## B9 `rm` 对接真实 Windows 回收站

- **现状**：`rm` 默认把文件搬到 `~/.filex/trash`（`internal/ops/file_ops.go:338`），**不是** Windows 回收站；本轮已把 README × 2、SKILL.md、`help.go`、MCP tool description 的"回收站"措辞全部更正为"恢复目录"。
- **移出理由**：文档与实现对齐即可消除误导，改实现是另一回事 —— 走 `SHFileOperation`/`IFileOperation` 需要 COM 与 apartment 初始化，且删除后由 shell 决定何时真正清空，filex 无法再承诺保留策略。
- **重启条件**：用户明确需要在 Windows 资源管理器回收站里看到 filex 删除的文件（而非用 `filex trash restore`，见 B6）。
- **预估**：M
